= jMolecules ArchUnit rules

This module contains https://www.archunit.org/[ArchUnit] rules to verify the integrity of domain concepts expressed via https://github.com/xmolecules/jmolecules#expressing-ddd-concepts[jMolecules DDD annotations or types].

To use these rules, declare the following artifact as dependencies of your project:

.Maven dependency
[source,xml]
----
<dependency>
  <groupId>org.jmolecules.integrations</groupId>
  <artifactId>jmolecules-archunit</artifactId>
  <version>${jmolecules-integrations.version}</version>
  <scope>test</scope>
</dependency>
<dependency>
  <groupId>com.tngtech.archunit</groupId>
  <artifactId>archunit-junit5</artifactId>
  <version>${archunit.version}</version>
  <scope>test</scope>
</dependency>
----

The provided rules can then be used in a JUnit test as follows:

[source, java, tabsize="2"]
----
import static org.assertj.core.api.Assertions.*;

import com.tngtech.archunit.core.domain.*;
import com.tngtech.archunit.junit.*;
import com.tngtech.archunit.lang.*;

import org.jmolecules.archunit.*;

@AnalyzeClasses(packages = "example") // <1>
class JMoleculesRulesUnitTest {

  @ArchTest ArchRule dddRules = JMoleculesDddRules.all(); // <2>
  @ArchTest ArchRule onion = JMoleculesArchitectureRules.ensureOnionSimple(); // <2>

  // alternatively

  @ArchTest // <3>
  void detectsViolations(JavaClasses classes) {

    EvaluationResult result = JMoleculesDddRules.all().evaluate(classes);

    assertThat(result.hasViolation()).isFalse();
  }
}
----
<1> The `@AnalyzeClasses(…)` annotation defines the scope of the classes to be verified.
This is likely to be the base package of your application.
<2> The property style architecture definition can be used simply declaring the rule as a field annotated with `@ArchTest`.
ArchUnit will verify the classes pointed to by <1> and the test will fail if violations occur.
<3> If you prefer to manually evaluate the violations, you can also declare a method annotated with `@ArchTest` and get the classes scanned for handed in as method argument.

For detailed information about the rules, be sure to check out the types and method definitions in  https://github.com/xmolecules/jmolecules-integrations/blob/main/jmolecules-archunit/src/main/java/org/jmolecules/archunit[`org.jmolecules.archunit`].

== Customizing the architecture rules

The rules for the Hexagonal, Onion and Layered Architecture each come with an options type (`HexagonalVerificationOptions`, `OnionVerificationOptions` and `LayeredVerificationOptions`) to customize them, e.g. the way stereotypes are looked up, the depth of the verification, or the scope the rule is applied to.
Start with the `defaults()` and derive customized instances from there.

[source, java]
----
var options = HexagonalVerificationOptions.defaults()
  .withDepth(VerificationDepth.SEMI_STRICT) // <1>
  .withScope(JavaClass.Predicates.resideInAPackage("example.orders")); // <2>

@ArchTest ArchRule hexagonal = JMoleculesArchitectureRules.ensureHexagonal(options);
----
<1> Configures how much access to non-port application code is allowed within Hexagons. `SEMI_STRICT` allows secondary adapters to access application code (to avoid too many application types, such as aggregates and identifiers having to be moved to secondary ports). `LENIENT` allows primary adapters to access application code and secondary adapters directly.
<2> Restricts the verification to the given types. References from or to types outside the scope are ignored.

=== Architectural units

Annotations meta-annotated with `@ArchitecturalUnit` (e.g. `@Module`, `@Hexagon`, `@Onion` or `@Layered`) declare packages as _architectural units_.
The Hexagonal, Onion and Layered rules are then applied to each unit using the language individually, and once to the code outside of any unit, i.e. references within a unit (and to code outside of any unit) are subject to the usual layering rules.
References between units are governed by the roles a unit exposes and the roles that may refer to other units, as described below.
A unit uses a language if at least one of its types is assigned a stereotype of it, or if it is declared via `@Hexagon`, `@Onion` or `@Layered`.
For the Hexagonal Architecture, by default, only secondary adapters may refer to other units, and only to their primary adapters.
For the Onion Architecture, by default, only infrastructure ring types may refer to other units, and only to their infrastructure ring types.
For the Layered Architecture, by default, only application and domain layer types may refer to other units, and only to their application and domain layer types.
All layers can be exposed and allowed to refer to other units, usually the lower layers of a unit being exposed to the upper ones of others.

NOTE: `ensureLayering()` and `ensureLayeringStrict()` don't consider architectural units, as their return type (`LayeredArchitecture`) can't express that.
They're deprecated in favor of `ensureLayering(LayeredVerificationOptions)` and `ensureLayeringStrict(LayeredVerificationOptions)`.

==== Customizing Exposure and Referrers

The options allow configuring which roles a unit exposes to other units and which of its roles may refer to other units:

[source, java]
----
var options = HexagonalVerificationOptions.defaults()
  .withExposure(Exposure.PRIMARY_ADAPTERS, Exposure.PRIMARY_PORTS) // <1>
  .withReferrers(Referrer.SECONDARY_ADAPTERS, Referrer.APPLICATION); // <2>
----
<1> Other units may refer to a unit's primary adapters and primary ports.
<2> Secondary adapters and application code (including types without hexagonal stereotypes) may refer to other units.

Secondary ports can be exposed via `Exposure.SECONDARY_PORTS`, e.g. to allow other units to use a repository directly instead of going through a primary port and the application code. Declaring that on the unit documents the design decision.

Primary adapters (infrastructure ring types for the Onion Architecture) by default are only ever exposed to secondary adapters (infrastructure ring types) of other units.
Individual units can replace the global settings via the `exposes` and `refersVia` attributes of `@Hexagon`, `@Onion` and `@Layered`:

[source, java]
----
@Hexagon(exposes = Exposure.PRIMARY_PORTS, refersVia = Referrer.SECONDARY_ADAPTERS)
package example.orders;
----

Here, other units may only refer to the primary ports of `example.orders`, and only the hexagons secondary adapters may refer to other units, independently of the general options configured.

To add roles to the globally configured ones (or the ones declared via `exposes` and `refersVia`) instead of replacing them, use `additionallyExposes` and `additionallyRefersVia`.
The options offer the same via `withAdditionalExposure(…)` and `withAdditionalReferrers(…)`:

[source, java]
----
@Hexagon(additionallyExposes = Exposure.SECONDARY_PORTS)
package example.orders;
----

[source, java]
----
var options = HexagonalVerificationOptions.defaults()
  .withAdditionalExposure(Exposure.SECONDARY_PORTS);
----

The referrers setting only applies to units using a particular architectural language.
In units not using it, as well as in code outside of any unit, any type may refer to other units, but only to the types those units expose.

==== Direct Application-Level Access

`withDirectApplicationAccess()` on the Hexagonal, Onion and Layered options allows the application core (application code including types without stereotypes of the language, as well as primary and secondary ports for the Hexagonal Architecture) to refer to the application code and primary ports (application ring and layer types for the Onion and Layered Architecture) of other units, as well as to all types of units not using the language.
That access is granted independently of the exposure and referrers configured, globally or on the individual units.
`withoutDirectApplicationAccess()` disables it again.
All other references, e.g. secondary adapters referring to primary ports of other units, still require the roles to be exposed explicitly.

To only verify the references between units, e.g. to combine that with a verification of the units' internals set up separately, use `ensureHexagonalUnitBoundaries(…)`, `ensureOnionSimpleUnitBoundaries(…)`, `ensureOnionClassicalUnitBoundaries(…)` or `ensureLayeringUnitBoundaries(…)`.
They don't apply the layer and ring rules.

==== Customizing Unit Resolution

Frameworks with their own notion of modules can provide an `ArchitecturalUnitResolver` via the options to define the units themselves.

NOTE: As of jMolecules 2.1, packages annotated with `@Module` are architectural units, too.
Code bases combining them with hexagonal or onion stereotypes might see new violations for references between modules.
To verify the architecture as before, i.e. without considering any architectural units, opt out via `ArchitecturalUnitResolver.none()`:

[source, java]
----
var options = HexagonalVerificationOptions.defaults()
  .withUnitResolver(ArchitecturalUnitResolver.none());

@ArchTest ArchRule hexagonal = JMoleculesArchitectureRules.ensureHexagonal(options);
----
